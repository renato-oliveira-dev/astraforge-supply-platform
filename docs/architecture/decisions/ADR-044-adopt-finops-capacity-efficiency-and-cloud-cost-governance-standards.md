# 1. Context

Cloud infrastructure changes the economics of software systems.

Traditional infrastructure frequently follows:

```text
PLAN
  |
  v
PURCHASE
  |
  v
PROVISION
  |
  v
USE FOR YEARS
```

Cloud infrastructure instead enables:

```text
PROVISION
   |
   v
CONSUME
   |
   v
PAY
   |
   v
SCALE
   |
   v
PAY MORE / LESS
```

This flexibility creates significant engineering advantages, but also allows inefficient architectures to generate continuously increasing operational cost.

Typical cost drivers include:

```text
Compute

Kubernetes

PostgreSQL

Kafka

Redis

Storage

Network Egress

Logging

Observability

Backup

Non-Production Environments
```

Cost therefore becomes an architectural characteristic.

# 4. Decision

The platform adopts FinOps as a shared engineering, platform and business discipline.

The canonical model is:

```text
                 BUSINESS DEMAND
                       |
                       v
                    TRAFFIC
                       |
                       v
                   CAPACITY
                       |
                       v
                 CLOUD USAGE
                       |
                       v
                     COST
                       |
              +--------+--------+
              |                 |
              v                 v
          RELIABILITY       EFFICIENCY
              |                 |
              +--------+--------+
                       |
                       v
                  OPTIMIZATION
```

Cost must be optimized together with reliability and performance.

# 5. Fundamental Principle

The primary rule is:

```text

not merely a finance report.
```

# 32. Budget

Material services/platform capabilities should have budget expectations.

---

# 33. Budget Is Not Hard Runtime Limit

A financial budget should not automatically terminate production capacity.

---

# 34. Why

A hard budget cutoff can transform:

```text
Cost Overrun
```

into:

```text
Production Outage
```

---

# 35. Budget Alert

Budget thresholds should generate alerts before material overruns.

---

# 36. Suggested Threshold Model

Conceptually:

```text
50%  -> informational

80%  -> warning

100% -> escalation

120% -> urgent review
```

Actual thresholds depend on organizational policy.

---

# 37. Forecasting

Cost governance should consider forecasted spend, not only accumulated spend.

---

# 38. Forecast Signal

If projected monthly cost materially exceeds budget, teams should be notified before month-end.

---

# 39. Cost Anomaly Detection

Unexpected cost changes must be detectable.

---

# 40. Examples

```text
Sudden logging increase

Unexpected data transfer

Runaway autoscaling

Abandoned database

Kafka retention growth

High-cardinality metrics

Unbounded object storage
```

---

# 41. Anomaly Is Not Automatically Waste

Cost increases may represent legitimate traffic/business growth.

---

# 42. Investigation

Cost anomalies require correlation with:

- traffic
- releases
- incidents
- capacity
- business volume

---

# 43. Unit Economics

Where practical, cost should be related to business throughput.

---

# 44. Examples

```text
Cost per Order

Cost per Checkout

Cost per 1,000 API Requests

Cost per Invoice Processed
```

---

# 45. Why Unit Economics

Total cost alone cannot distinguish:

```text
More cost because of waste
```

from:

```text
More cost because business volume doubled.
```

---

# 46. Example

If:

```text
Monthly Cost = R$ 100.000

Orders = 1.000.000
```

then:

```text
Cost per Order = R$ 0,10
```

If monthly cost grows to:

```text
R$ 150.000
```

while volume grows to:

```text
2.000.000 orders
```

cost per order becomes:

```text
R$ 0,075
```

Total cost increased, while unit efficiency improved.

---

# 47. Cost Metric Context

Cost dashboards should therefore include both:

```text
ABSOLUTE COST

and

UNIT COST
```

where meaningful.

# 48. Capacity Planning

Capacity planning must combine:

```text
Historical Demand

Expected Growth

Peak Demand

Failure Scenarios

SLO Requirements
```

---

# 49. Average Load Is Insufficient

Capacity must not be sized solely against average traffic.

---

# 50. Peak Capacity

Systems must accommodate justified peak demand.

---

# 51. Failure Capacity

Capacity planning must consider failure modes.

Example:

```text
3 replicas normally
```

must not automatically mean all three can operate at 100% CPU continuously.

---

# 52. Headroom

Critical services require sufficient capacity headroom.

---

# 53. Excessive Headroom

Large permanent unused headroom is also a cost signal.

---

# 54. Rightsizing

Resources should be periodically compared against actual usage.

---

# 55. Rightsizing Inputs

Use:

- CPU utilization
- memory utilization
- latency
- throttling
- GC
- saturation
- queue depth
- traffic

---

# 56. CPU Alone Is Insufficient

Low CPU does not necessarily imply overprovisioning.

The service may be constrained by:

- memory
- I/O
- latency
- network
- database
- concurrency

---

# 57. Kubernetes Requests

CPU and memory requests must reflect realistic workload requirements.

---

# 58. Requests Purpose

Requests affect:

- scheduling
- capacity reservation
- autoscaling
- cluster efficiency

---

# 59. Excessive Requests

Large unused requests waste schedulable cluster capacity.

---

# 60. Insufficient Requests

Very small requests may create:

- contention
- unstable scheduling
- misleading utilization
- performance degradation

---

# 61. Memory Request

Memory requests should reflect normal working-set requirements with justified margin.

---

# 62. CPU Request

CPU requests should reflect sustainable baseline demand.

---

# 63. Kubernetes Limits

Limits require workload-specific consideration.

---

# 64. Memory Limit

Memory limits must account for JVM behavior.

---

# 65. JVM Container Awareness

Java 21 container-aware memory behavior must be considered when sizing:

- heap
- metaspace
- thread stacks
- native memory
- direct buffers

---

# 66. Heap Is Not Container Memory

This assumption is incorrect:

```text
Container Memory = JVM Heap
```

---

# 67. Memory Model

Conceptually:

```text
CONTAINER MEMORY
       |
       +--> Heap
       +--> Metaspace
       +--> Thread Stacks
       +--> Direct Buffers
       +--> Native Memory
       +--> JVM Runtime
```

---

# 68. OOMKilled

Repeated `OOMKilled` events are capacity/configuration failures and must not be treated simply by repeatedly increasing limits without analysis.

---

# 69. CPU Limits

CPU limits can cause throttling.

Their use must consider latency-sensitive Java workloads.

---

# 70. HPA

Horizontal Pod Autoscaler should be used where workload characteristics justify horizontal scaling.

---

# 71. HPA Signal

CPU is not always the best scaling signal.

---

# 72. Alternative Signals


# 73. Business Scaling Metric

- availability

# 75. Maximum Replicas

- runaway cost

- database exhaustion
- connection storms

# 76. Autoscaling Does Not Create Infinite Capacity

---

# 77. Downstream Capacity

```text

Kafka Partitions

External API Limits

Redis Connections

Thread Pools
```

---

# 78. Scale-Out Cost

---

# 79. Vertical Scaling

Vertical scaling may be appropriate for some workloads.

---

# 80. Horizontal vs Vertical

The decision should be workload-driven rather than ideological.

# 81. Cluster Autoscaling

# 83. Bin Packing

# 84. Node Families

# 85. Architecture Benchmark

# 86. Spot Capacity

# 88. Reserved Capacity

Stable baseline workloads may benefit from committed/reserved pricing models.

# 89. Commitment Risk

# 94. Query Optimization Before Scaling

Before permanently increasing database capacity, investigate expensive queries and indexes.

# 95. Bad Query Scaling

# 96. Index Cost

Indexes improve reads but consume:

- storage
- memory
- write I/O
- maintenance

Unused/redundant indexes should be reviewed.

# 97. Connection Cost

# 98. Connection Budget

Connection pools must be sized against database capacity.

# 99. Example

# 100. Connection Pool Sizing

More connections do not automatically mean more throughput.

---

# 101. Read Replica

- read scalability
- availability
- reporting isolation

not added reflexively.

---

# 102. Storage Growth

Database storage growth must be monitored and forecast.

---

# 103. Backup Cost

Retention policies affect backup cost.

---

# 104. Retention

Backup retention must satisfy recovery/compliance requirements without retaining unnecessary copies indefinitely.

---

# 105. Redis Cost Governance

Redis cost is strongly influenced by memory.

---

# 106. Cache Only What Has Value

Do not cache data merely because Redis is available.

---

# 107. TTL

Cached data should generally have explicit TTL where semantics permit.

---

# 108. Unbounded Cache

Unbounded cache growth is prohibited.

---

# 109. Cache Payload Size

Large cached payloads should be measured.

---

# 110. Cache Duplication

Duplicating large datasets in many cache structures requires justification.

---

# 111. Cache Hit Ratio

A cache with low hit ratio and significant memory cost should be reevaluated.

---

# 112. Eviction

Eviction policy must match cache semantics.

---

# 113. Redis as Database

Redis should not become an accidental expensive primary database without an explicit architectural decision.

---

# 114. Kafka Cost Governance

- throughput
- partitions
- replication
- retention
- storage
- network

# 116. Excessive Partitions

- metadata
- broker load

- operational complexity

# 117. Insufficient Partitions

Under-partitioning may prevent required consumer parallelism.

---

# 118. Retention

Kafka retention should reflect business/replay requirements.

---

# 119. Infinite Retention

Indefinite retention must not be the default.

---

# 120. Event Payload

Large event payloads increase:

- network
- storage
- producer cost
- consumer cost

---

# 121. Event Duplication

Publishing redundant large events should be avoided.

---

# 122. Consumer Lag

Consumer lag can become a capacity signal.

---

# 123. Lag-Based Scaling

Kafka consumers may scale based on lag where partition count and processing semantics permit.

---

# 124. Logging Cost

Logs are not free.

---

# 125. Log Volume

Excessive log volume increases:

- ingestion
- storage
- indexing
- query cost

---

# 126. Production DEBUG

Persistent DEBUG logging in production is prohibited unless explicitly required for temporary diagnosis.

---

# 127. Large Payload Logging

Logging full large request/response payloads is discouraged for both:

- security
- cost

reasons.

---

# 128. Duplicate Logging

The same failure should not be redundantly logged by every architectural layer without diagnostic value.

---

# 129. Stack Traces

Stack traces should be emitted where they aid diagnosis, not indiscriminately for expected business outcomes.

---

# 130. Observability Cardinality

# 131. Prohibited Metric Dimensions


# 132. Trace Sampling

# 133. Sampling Strategy

# 134. Observability Retention

Log, metric and trace retention should match operational/compliance needs.

# 135. More Retention Is Not Automatically Better

# 136. Storage Lifecycle

# 142. Network Cost

# 207. Cost Governance Gate

A production service is not considered fully cost-governed until:

```text
[ ] Cost owner identified

[ ] Service ownership identified

[ ] Environment identified

[ ] Required tags configured

[ ] Cost allocation available

[ ] Production/non-production cost separable

[ ] Budget or expected spend defined

[ ] Forecast visible

[ ] Cost anomaly detection configured

[ ] Major resources rightsized

[ ] Kubernetes requests reviewed

[ ] Kubernetes limits reviewed

[ ] Autoscaling configured where applicable

[ ] Autoscaling maximum protects dependencies

[ ] Database connections budgeted

[ ] PostgreSQL growth monitored

[ ] Redis memory/TTL reviewed

[ ] Kafka partitions reviewed

[ ] Kafka retention reviewed

[ ] Logging volume reviewed

[ ] Metric cardinality reviewed

[ ] Trace sampling reviewed

[ ] Storage lifecycle reviewed

[ ] Network egress understood

[ ] Non-production lifecycle reviewed

[ ] Ephemeral resources have TTL

[ ] Idle-resource detection available

[ ] Unit economics defined where useful

[ ] SLO guardrails protect optimization

[ ] Cost alerts have owner
```

# 208. Anti-Patterns

The following are prohibited or strongly discouraged:

- treating cloud cost solely as a finance problem
- resources without ownership
- production resources without required allocation metadata
- optimizing cost without considering SLOs
- duplicating production capacity in every environment without justification
- hard budget controls that unexpectedly stop production
- scaling based solely on average load
- arbitrary Kubernetes requests/limits
- assuming JVM heap equals container memory
- unbounded autoscaling
- scaling applications without considering database connections
- permanently increasing database size before investigating inefficient SQL
- unbounded Redis caches
- Kafka retention without business justification
- excessive Kafka partitions without throughput/parallelism justification
- permanent DEBUG logging in production
- high-cardinality metrics using business identifiers
- unlimited telemetry retention
- temporary cloud resources without TTL
- abandoned PR environments
- orphaned persistent volumes/snapshots
- unnecessary cross-region traffic
- remote-call N+1
- automatically deleting resources solely because utilization appears low
- automatically downsizing critical production resources without safeguards
- spending more engineering effort than the optimization can reasonably recover
- measuring FinOps success only by absolute spend reduction

The decision provides:

- clearer cloud cost ownership
- improved cost visibility
- better capacity efficiency
- reduced idle infrastructure
- safer autoscaling
- improved Kubernetes utilization
- controlled database growth
- lower telemetry waste
- better non-production lifecycle
- improved forecasting
- better unit economics
- cost-aware architecture decisions

# 210. Negative Consequences

The decision introduces:

- tagging governance
- cost dashboards
- budget management
- anomaly triage
- rightsizing reviews
- additional engineering metrics
- periodic FinOps reviews

These costs are accepted because unmanaged cloud waste compounds continuously.

# 211. Neutral Consequences

The decision also means:

- higher absolute cost may be healthy when business volume grows
- lower absolute cost may be unhealthy if reliability is degraded
- some spare capacity is intentional
- not every recommendation should be automated
- managed services may cost more directly while reducing TCO
- cost optimization remains contextual

# 213. Implementation Guidance

The following rules are mandatory:

1. Material production services require identifiable cost ownership.
2. Cost ownership should align with service ownership.
3. Mandatory cloud allocation metadata should be automated where practical.
4. Production and non-production spend must be distinguishable.
5. Budgets must provide visibility and escalation rather than blindly terminate production.
6. Material cost anomalies require investigation.
7. Unit economics should be used where meaningful.
8. Capacity planning must consider peak and failure scenarios.
9. Rightsizing must use multiple workload signals.
10. Kubernetes requests/limits require workload-specific sizing.
11. Java container sizing must include non-heap JVM memory.
12. Autoscaling must account for downstream capacity.
13. Autoscaling requires reasonable maximum bounds.
14. Database connection pools must be evaluated across all replicas.
15. Query/index optimization should precede unnecessary permanent DB scaling.
16. Redis caches require bounded memory behavior.
17. Kafka partition and retention decisions require workload justification.
18. Production DEBUG logging must not remain enabled without explicit reason.
19. High-cardinality observability dimensions must be controlled.
20. Telemetry retention requires explicit operational value.
21. Temporary resources require lifecycle/TTL controls.
22. Idle resources should be detected automatically.
23. Resource deletion requires ownership/dependency validation.
24. Cross-region/network egress requires architecture consideration.
25. Remote-call N+1 patterns must be treated as performance and cost defects.
26. Cost optimization must preserve agreed SLOs.
27. Material capacity reductions must be observable and reversible.
28. FinOps recommendations should not automatically override engineering context.
29. Large cost regressions should be correlated with releases and workload changes.
30. Material services require periodic cost review.
31. Cost governance should increasingly become policy/fitness functions where safe.
32. Optimization prioritization should consider expected financial return and engineering effort.

# 220. Decision Summary

The definitive cost model is:

```text
                    BUSINESS VALUE
                          |
                          v
                       TRAFFIC
                          |
                          v
                       CAPACITY
                          |
                          v
                     CLOUD COST
                          |
              +-----------+-----------+
              |                       |
              v                       v
         RELIABILITY              EFFICIENCY
              |                       |
              +-----------+-----------+
                          |
                          v
                     OPTIMIZATION
```

The target is not:

```text
COST
 |
 v
MINIMUM
```

but:

```text
                 BUSINESS REQUIREMENT
                         +
                        SLO
                         +
                      SECURITY
                         +
                     CAPACITY
                         |
                         v
               LOWEST JUSTIFIED TCO
```

Cost ownership follows service ownership:

```text
SERVICE
   |
   +--> TEAM
   |
   +--> INFRASTRUCTURE
   |
   +--> COST
   |
   +--> SLO
```

For Kubernetes:

```text
             ACTUAL WORKLOAD
                    |
          +---------+---------+
          |                   |
          v                   v
      REQUESTS              LIMITS
          |                   |
          +---------+---------+
                    |
                    v
                 HPA/VPA
                    |
                    v
              CLUSTER CAPACITY
```

For Java:

```text
CONTAINER MEMORY
      |
      +--> Heap
      +--> Metaspace
      +--> Thread Stacks
      +--> Direct Buffers
      +--> Native Memory
```

Therefore:

```text
-Xmx = container limit
```

must not be assumed safe.

For autoscaling:

```text
MORE TRAFFIC
     |
     v
MORE PODS
     |
     +--------> MORE DB CONNECTIONS
     |
     +--------> MORE REDIS CONNECTIONS
     |
     +--------> MORE DOWNSTREAM CALLS
     |
     +--------> MORE COST
```

Autoscaling therefore requires system-level capacity analysis.

For databases:

```text
SLOW SYSTEM
    |
    v
INVESTIGATE
    |
    +--> Query?
    +--> Index?
    +--> Lock?
    +--> Connection Pool?
    +--> I/O?
    |
    v
SCALE ONLY WHEN JUSTIFIED
```

For non-production:

```text
TEMPORARY RESOURCE
        |
        v
       OWNER
        |
        v
       TTL
        |
        v
AUTO CLEANUP
```

For unit economics:

```text
TOTAL COST
    /
BUSINESS VOLUME
    =
UNIT COST
```

This distinguishes growth from waste.

The optimization loop is:

```text
             MEASURE
                |
                v
             ANALYZE
                |
                v
            OPTIMIZE
                |
                v
             DEPLOY
                |
                v
             OBSERVE
                |
        +-------+-------+
        |               |
        v               v
     SLO OK?          SLO BAD?
        |               |
        v               v
      KEEP           ROLLBACK
```

The complete FinOps model is:

```text
COST VISIBILITY
      +
OWNERSHIP
      +
UNIT ECONOMICS
      +
CAPACITY MANAGEMENT
      +
AUTOMATION
      +
SLO GUARDRAILS
      =
SUSTAINABLE CLOUD EFFICIENCY
```

The governing principle is:

```text
The cheapest architecture
is not the architecture with
the smallest infrastructure bill.

It is the architecture that delivers
the required business capability,
reliability, security and performance
with the lowest justified total cost
of ownership.
```
